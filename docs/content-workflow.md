# 内容创作工作流（v0.2，已在 Skill v0.7.0 实现）

> 状态：作者 2026-10-17 确认 v0.1 草案后，Skill 按本文档重构；目录风格按作者要求参考了一位创作者公开分享的写作 Skill 结构（工作台下分 `风格参考/`、`写作技巧/`、`规范指南/`、`我的项目/`，Skill 内分 `references/`、`scripts/`、`templates/`）。只借鉴目录组织方式，参考文档的内容全部重新调研、注明来源。
> 出发点：一篇内容的价值由读者决定，可信度由作者署名承担。AI 负责把研究、起草和打磨做快做稳，判断和真实经历留给作者。

运行时的权威说明是 [SKILL.md](../skills/ai-knowledge/SKILL.md) 和它链接的参考文档；本文记录设计思路，两者不一致时以 Skill 为准。

## 1. 五条原则

1. **先定角度，再动笔。** 写错方向的文章，改得再好也没用。动笔前作者至少确认一次"写什么、给谁看、读完得到什么"。
2. **真实是底线。** 经历、实测数据、引用只能来自作者或可查的来源。AI 不替作者"用了两周"，也不替作者"测下来省 3 小时"。
3. **作者做判断，AI 做体力活。** 搜资料、列方案、起草、核对格式、改编平台版本交给 AI；选角度、补经历、拍板发布由作者来。
4. **一次写透，多处分发。** 先写一篇完整的主稿，其他平台从主稿改编，不各写各的。
5. **每篇都让下一篇更好。** 资料可以复用，作者的修改会变成规则，发布数据会反过来影响选题。

## 2. 全流程总览

```text
 选题库 ──▶ ① 接需求 ──▶ ② 调研 ──▶ ③ 选角度 ◆ ──▶ ④ 备素材 ◇ ──▶ ⑤ 搭结构
                                                                    │
 ⑪ 复盘学习 ◀── ⑩ 发布归档 ◆ ◀── ⑨ 平台改编 ◀── ⑧ 配图 ◀── ⑦ 打磨四遍 ◀── ⑥ 写初稿

 ◆ 作者确认点（快速模式只保留 ⑩）    ◇ 作者任务（需要实测、截图或经历时才有）
```

| 阶段 | 步骤 | 一句话 |
| --- | --- | --- |
| 准备 | ① 接需求 → ② 调研 → ③ 选角度 | 弄清楚为谁写、写什么，事实先弄对 |
| 素材 | ④ 备素材 → ⑤ 搭结构 | 拿到真实的料，排好讲的顺序 |
| 创作 | ⑥ 写初稿 → ⑦ 打磨四遍 → ⑧ 配图 | 写出来，再改到敢署名 |
| 分发 | ⑨ 平台改编 → ⑩ 发布归档 | 一稿多发，留下记录 |
| 成长 | ⑪ 复盘学习 | 把这一篇的经验变成下一篇的规则 |

## 3. 三种协作强度

| 强度 | 什么时候用 | 停几次 |
| --- | --- | --- |
| 快速 | 短内容、急稿，或作者说"直接写" | 不停。AI 自选角度并写明理由，作者任务列进核验记录 |
| 标准（默认） | 大多数文章 | 第 ③ 步停一次确认角度；需要实测时第 ④ 步再停一次 |
| 深度 | 重要稿件、系列开篇、个人品牌代表作 | 角度、结构、初稿各停一次 |

不管哪种强度，第 ⑩ 步"可以发布"都只能由作者说。

## 4. 内容工作台

所有内容集中放在一个**内容工作台**，不散落在各个代码项目里。代码项目只是素材来源，只读不写。查找顺序：请求里的路径 → 环境变量 `AI_KNOWLEDGE_WORKSPACE` → 个人配置目录 `settings.json` 的 `workspace`；都没有时退回当前项目的 `docs/knowledge/<topic-slug>/`。

```text
<内容工作台>/
├── 用户人设.md            # 作者是谁、写给谁、能说什么（作者维护）
├── 风格参考/              # 作者自己数据好的文章，作文风样板（作者维护）
├── 写作技巧/              # 作者整理的写作方法，优先于 Skill 通用技法（作者维护）
├── 规范指南/              # 作者更新的平台规范、口播话术、运营结论（作者维护）
└── 我的项目/              # 以下由流程写入
    ├── _briefs/           # 需求卡 <YYYYMMDD>-<slug>.md（含角度方案和作者选择），选题库.md
    ├── _knowledge_base/   # 资料卡 <领域>/<YYYYMMDD>-<问题>.md，跨文章复用
    ├── _协作文档/          # 作者任务单 <YYYYMMDD>-<slug>.md（需要时才有）
    ├── 公众号写作/<YYYYMMDD>-<slug>/
    │   ├── article.md     # 主稿，唯一要发表的长文
    │   ├── review.md      # 核验记录，只给作者看；含当前阶段和发布记录
    │   └── assets/        # 封面、解释图和台账
    ├── 推文写作/<YYYYMMDD>-<slug>/      # xiaohongshu.md、weibo.md、x.md
    ├── 短视频逐字稿/<YYYYMMDD>-<slug>/   # 口播稿.md
    └── 历史存档/          # 发布后按上面三个子目录原样移入，另有 数据复盘.md
```

写作规则和视觉品牌仍放在个人配置目录；工作台根目录的四项由作者维护，Skill 只读。`scripts/create_project.py` 建目录和需求卡，`scripts/save_article.py` 归档，都是可选的。

v0.1 草案里的 `inbox.md`、`topics.md`、`research/`、`projects/`、`angles.md`、`tasks.md`、`outline.md`、`platforms/`、`published.md` 分别并入：选题库、`_knowledge_base/`、按平台分开的写作目录、需求卡（角度方案）、`_协作文档/`、review.md（结构摘要、发布记录）和 `数据复盘.md`。

## 5. 每一步用到的参考文档

| 步骤 | AI 做什么 | 作者做什么 | 产出 | 参考文档 |
| --- | --- | --- | --- | --- |
| ① 接需求 | 判断类型，读人设，补默认值，最多问 3 个问题 | 回答，或说"按默认" | 需求卡 | 用户人设-快速参考、调研-讲解/复盘/测评/观点 |
| ② 调研 | 先查资料卡，再查一手来源，建证据表 | 提供素材 | 资料卡、证据表 | 调研-资料卡、对应类型的调研指南 |
| ③ 选角度 ◆ | 2–3 个取向不同的方案并推荐一个 | 选定、合并或否掉 | 需求卡的角度方案 | 选题与角度 |
| ④ 备素材 ◇ | 写能照着做的任务单 | 实测、截图、回答经历问题，或跳过 | 协作文档 | 协作文档与真实经历 |
| ⑤ 搭结构 | 结论先行，每节回答一个读者问题 | 深度模式确认结构 | 提纲 | 写作技巧-金字塔原理 |
| ⑥ 写初稿 | 按写作技巧和作者风格写，只用已有素材 | 深度模式看初稿 | article.md | 内容写作技巧、偏航句用法、风格-加载/应用 |
| ⑦ 打磨四遍 | 事实、读者、文字（降 AI 味、查平台规则），交独立复查 | 可以亲自复查 | 修订稿、review.md | 打磨与核验、降AI味指南、自媒体防限流指南 |
| ⑧ 配图 | 封面和 2–4 张解释图，整组验收 | 确认审美 | assets/ | 视觉-品牌加载/美术方向/配图验收 |
| ⑨ 平台改编 | 按平台读法重组，查规则 | 提出要求 | 推文写作/、短视频逐字稿/ | 平台改编、口播引导话术、自媒体动画 |
| ⑩ 发布归档 ◆ | 报告状态；作者说发了才归档 | 说"可以发布"，自己发 | review.md、历史存档/ | 发布合同 |
| ⑪ 复盘学习 | 记录数据、对比终稿，提出候选结论 | 确认哪些写回 | 数据复盘.md、选题库、写作规则 | 运营沉淀、风格-改稿复盘/分析/写回 |

## 6. 文字标准

目标不是"让文章不像 AI 写的"，而是**每句话都有信息、读者读得顺**。完整做法见 [降AI味指南](../skills/ai-knowledge/references/降AI味指南.md)。

| 项目 | 参考（经验值，作者的写作规则优先） |
| --- | --- |
| 句子 | 长短交替；超过 40 字或多重"的"字修饰时检查能不能拆 |
| 段落 | 手机上不超过 5 行，一段一个意思 |
| 开头 | 第一屏内出现场景或结论（"前 150 字"是编辑经验，没有研究出处） |
| 小节 | 一节只回答一个问题，小标题写成判断 |
| 朗读 | 读着拗口的句子一律重写 |

v0.1 草案写过"句子以 15–25 字为主"，调研后没有找到出处，改成上面不设平均值的写法。

## 7. 状态

```text
需求 → 调研 → 待选角度 ◆ → 待作者素材 ◇ → 写作 → 打磨 → 待复查 → 可发布 ◆ → 已发布 → 已复盘
```

项目的当前阶段写在 review.md 的"发布状态"和需求卡开头。作者随时说"这篇到哪了"，AI 都能接着做。

## 8. 红线

- 不编造经历、数据、引用和截图内容；不把推测写成事实，也不把建议写成已经做过的事。
- 公司名、客户名、内部系统名和域名、真实业务代码、日志原文都不进公开稿件。需要代码时，重写一段原创演示。
- 不自动发布，不替作者确认。
- 别人的文章只学方法，不照搬内容、结构、人设和金句。
- 不以"规避 AI 检测"或"降重"为目标。

## 9. 已确定的决定

| 决定 | 结果 |
| --- | --- |
| 工作台位置 | 作者指定，查找顺序见第 4 节；没有时退回 `docs/knowledge/` |
| 默认协作强度 | 标准 |
| 内容类型 | 讲解 `explainer`、复盘 `retrospective`、测评 `evaluation`、观点 `opinion`，取代 Feature、Concept、Problem；AGENTS.md 同步修改 |
| 文件 | 主稿和核验记录仍是 `article.md`、`review.md`；新增需求卡、资料卡、协作文档、口播稿和用户人设模板 |
| 范围 | 作者要求一次做完，①–⑪ 和全部参考文档在 v0.7.0 一起实现 |
| 证据类型 | 新增"公开资料"（带访问日期）和"实测记录"（只来自作者回填的协作文档） |

## 附：重构后怎么验收

1. 准备 4 条测试请求，每种内容类型一条，再加一条"直接写"的快速模式请求。
2. 每条都检查：有没有在该停的地方停下来；有没有编造经历；每个关键结论能不能找到依据；文字是否符合第 6 节的标准；平台规则检查有没有写进 review.md。
3. 在一个真实业务项目上跑一篇复盘，再找一个 AI 工具跑一篇测评，由作者判断"敢不敢直接署名发表"。
