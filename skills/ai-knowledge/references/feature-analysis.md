# Feature：功能开发复盘

## 确定分析范围

先读项目说明和目录索引，再按功能名、路由、接口、配置键定位入口；从入口沿调用链阅读必要模块与测试。避免无差别读取整个仓库、依赖目录、历史聊天或密钥文件。

- 指定 Commit：验证引用存在，再读提交摘要、变更文件和相关上下文。
- 指定范围：说明比较的是两端树差异还是分支共同祖先后的变化。不要擅自把 `A..B` 改成 `A...B`；不明确时说明采用的比较语义。
- 无范围：按功能名定位当前实现，记录当前 Commit（有 Git 时）以及是否包含未提交修改。不能把工作区状态误说成某个提交内容。
- 只有 Diff：可分析改动，但调用者、旧版本与运行效果未必可知；标注片段边界。
- 无源码或访问失败：输出已知业务与通用机制，列出需要的入口或配置，不发明文件、类、方法。

读取 Git 时使用只读命令，如 `git status --short`、`git log`、`git show`、`git diff`；引用来自用户时按参数处理，不能拼成可执行命令。避免外部 diff/helper 执行；不 checkout、reset 或修改代码来方便分析。

## 按机制而非文件组织

建立 `业务步骤 → 输入/输出 → 执行模块/符号 → 证据` 表。提炼少量核心抽象及关系，画业务主流程，必要时再画技术时序。

讲解顺序：

1. 原先的业务问题和使用者期望。
2. 最小解决机制；哪些参与者协作，哪里发生状态变化。
3. 前置概念与主流程，用一个完整例子贯穿。
4. 映射到实现：开源或用户授权公开的项目可以引用真实类、方法和配置；私有项目改写成原创演示。只摘最能说明机制的代码。
5. 错误分支、设计权衡与工程经验。

解释“为什么这样设计”必须有证据：设计文档或提交说明可归为作者意图；从代码反推只可写“这种设计的可能收益”，不能代替开发者发言。静态检查发现检查逻辑，不等于真实运行成功。

## 三层结论

用语言明确区分“本实现已做”“协议/通用原理要求”“可选改进或待核实”。通用最佳实践缺少代码依据时不得写成本项目已有能力。框架负责的行为注明依赖及版本核实状态。

证据表的项目事实写路径、符号和行号或 Commit，只留在 review.md。文章不复制私有代码：把机制重写成一段原创演示，类名、包名、域名换成通用名称，并在代码前说明它是演示。演示能运行就实际运行并在 review.md 记录；没运行就不说能跑。验证情况分别写静态阅读、实际执行的测试和未做的集成测试。

## 从实现到文章

源码复盘最容易写成“调用链说明书”。文章要回答的是读者的问题：这个功能解决了什么麻烦、关键的那一步为什么不能省、换成读者自己的项目该注意什么。调用链和类名是证据，不是结构。

阅读时顺手记下两类素材：一是代码里最能体现设计意图的几行（会改写成演示放进正文）；二是“如果没有这一步会怎样”的反事实，它通常就是文章最有说服力的段落。项目里发现的缺陷（日志打印敏感值、被注释掉的校验）记进 review.md 的公开安全过滤，文章里只能写成通用的常见错误，不能写成这个项目存在的问题。
