# 配图与资产验收

## 默认配几张

默认一张封面加 2–4 张解释图。用户说“不要图”或“纯文字”时一张都不做，在 review.md 的“配图”里写明原因。用户指定数量时照做。

先完成正文和事实遍，再定图。每张图只回答一个问题，回答不了就不做：

| 文章需要 | 图的形态 | 验收重点 |
| --- | --- | --- |
| 封面：让人想点开 | 核心判断的短句 + 一个视觉隐喻或品牌角色 | 标题在安全带内，缩成手机缩略图仍可读 |
| 谁和谁协作、各持有什么 | 关系图：参与者和它们之间的通道 | 参与者名称与正文一致，箭头写清动作 |
| 先后顺序 | 时序图或编号步骤图 | 顺序和条件与证据一致，成功和失败分支分开 |
| 前后对比、做与不做 | 左右对照图 | 两边保持相同的位置和名称，只改变差异点 |
| 状态变化 | 状态图 | 只画合法转换 |
| 可核实的数值 | 程序化数据图，可与角色插画合成 | 数据来源、单位、刻度；比例与真实数据一致；模拟数据在图上标明 |
| 界面操作 | 用户授权的真实截图 | 先去敏；没有截图就不画假界面 |

能用一句话说清的内容不配图。不为凑数量画重复的图，不用装饰图替代解释图。

## 设计一张解释图

1. 先写一句“这张图回答什么”，写进 review.md 的配图表。
2. 列出节点和边：参与者 3–7 个，每条边写清是浏览器跳转、服务端调用、数据存储还是先后顺序。超过 7 个节点就按子问题拆图。
3. 逐条边对照证据表：服务端完成的动作不能画成浏览器完成，可选步骤要标“可选”。
4. 图上只放关键词和短句。完整解释留在正文，正文在图前或图后用一两句话把图里的关系说一遍。
5. 同一篇文章的图保持一致：同一参与者用同一颜色、图标和名称，配色和字号统一。材质、线条、主色用法、签名图形和版式标记按 [美术方向](美术方向.md) 执行，全部做完后把本篇的图放在一起做一次整组检查。

Mermaid 适合在上下文里打草稿，但大多数发布平台不渲染它。正文只嵌入导出后的 PNG。

## 制作与导出

- **程序化图解（没有可用生图工具时的默认做法）**：手写自包含 SVG，文字可编辑，再用可用的浏览器或渲染工具导出 PNG。SVG 不含脚本、事件、`style` 元素或属性、外部字体、图片和 CSS；需要位图时以 base64 内嵌 PNG/JPEG。
- **品牌角色**：按 [视觉品牌加载](品牌加载.md) 复用已验收的素材，或在生图工具能接收母版参考图时生成新图。工具无法传参考图时，不生成角色图，把需求写成待制作项。
- **生图工具**：能接收参考图时，可以整张画带角色的封面、流程图和插画，按 [美术方向](美术方向.md) 写一份出图说明。短标题和短标签可以由工具直接写，但必须放大逐字核对；数值比例、长段说明、代码和界面的分工见美术方向的"谁来画什么"。生成图上的节点、顺序和箭头同样要逐条对照证据表。

尺寸：封面按 1600×900（16:9）设计，标题放在垂直方向中间约 75% 的安全带内；解释图按 1080 像素宽设计，高度按内容。程序化 PNG 以 2 倍像素密度导出，保证高分屏清晰；生图工具的输出保持原始分辨率，只按目标比例裁切，台账写实际尺寸。

手机可读性：文章在手机上的显示宽度约 360–390 像素，1080 宽的图会缩小到三分之一左右。所以解释图上最小的字至少 32 像素（手机上约 11–12 像素），标题 48 像素以上；封面标题 80 像素以上。手机阅读的解释图优先竖向排列（上下堆叠的步骤卡、分组卡片），少用需要横向细看的多列时序图。导出后按 390 像素宽实际看一次，看不清就删字、拆图或放大，不靠缩小字号塞内容。

中文字体使用本机合法字体并写回退链，不打包字体文件。导出后检查文字碰撞、截断和缺字，记录实际使用的浏览器和字体。没有渲染工具时写明未验证。

## 文件与台账

所有图片放在主题目录的 `assets/` 下，正文用 `![有意义的 alt](./assets/<name>.png)`（必须以 `./assets/` 开头）引用。SVG 源文件同目录保留，供以后修改。不使用绝对路径、临时 URL 或越出主题目录的链接；未制作的图不写图片链接。

`assets/manifest.json` 记录每个文件：

```json
{
  "schemaVersion": "1",
  "brandId": "generic",
  "kitVersion": "none",
  "paletteStatus": "none",
  "batch": "2026-10-16-a",
  "status": "draft",
  "assets": [
    {
      "id": "cover",
      "type": "cover",
      "path": "./assets/cover.png",
      "status": "generated",
      "source": "文章核心判断与证据表 F01",
      "references": [],
      "method": "手写 SVG，浏览器导出 PNG",
      "width": 3200,
      "height": 1800,
      "sha256": "<文件的 SHA-256>",
      "review": {"identity": "na", "knowledge": "pass", "readability": "pass",
                 "rights": "local-only", "aesthetic": "pending"}
    }
  ]
}
```

- type：cover、infographic、chart、illustration、banner、profile-card。
- status：planned（未制作，必须写 reason）、generated（文件存在，待用户验收）、approved（用户明确批准，必须写 approval）、rejected。
- review：identity、knowledge、readability 取 pass / fail / pending / na；rights 取 local-only / pending / public；aesthetic 取 pending / pass / fail。人工审美只能由用户确认，写稿者填 pending。
- 使用品牌时 brandId、kitVersion、paletteStatus 与品牌配置一致，references 填用到的母版 ID。
- 正文嵌入的图必须已登记，状态为 generated 或 approved，且 identity、knowledge、readability 都是 pass 或 na。

可选检查命令：

```sh
python <skill-root>/scripts/visual_assets.py bundle <topic-directory>
python <skill-root>/scripts/visual_assets.py bundle <topic-directory> --brand <kit-directory>
```

检查器只核对文件、尺寸、hash、台账状态和 Markdown 图片链接；不能判断图是否准确、好看或有授权。这些在 review.md 的配图表里由人确认。
