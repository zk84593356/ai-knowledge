# 观点：把一个判断讲到别人愿意认真考虑

观点文章卖的是作者的判断。判断本身可以有立场，但支撑它的事实必须经得起查，反方也要被认真对待。读者读完可以不同意，却应该说得出作者为什么这样想。

## 先拆开：事实和判断

动笔前把作者的主张拆成两类句子：

| 类型 | 例子 | 需要什么 |
| --- | --- | --- |
| 事实陈述 | 这个框架去年发布了三个大版本 | 能查证的来源，进证据表 |
| 价值判断 | 小团队不该追着框架升级 | 理由和适用条件，进证据表记为“建议” |

Pew 研究中心在测试读者区分事实与观点时用的就是这个标准：事实陈述可以用证据证明或推翻，观点反映的是信念和价值，无法用证据完全证明。文章里两类句子都可以有，但不能把判断包装成事实，也不能用一个事实直接推出一个更大的判断。

## 核心判断要可以被反对

好的观点能被反对。“技术选型要结合实际”没人会反对，也就没有信息量；“三个人以下的团队，别自建 Kubernetes”有人会反对，这才值得写。

用 [选题与角度](选题与角度.md) 的核心判断格式写下来，再补一句“这个判断在什么情况下不成立”。说不出不成立的情况，判断通常太空。

## 理由和证据

每个支撑理由回答“为什么”，并配一种具体材料：数据、案例、作者亲历、可复现的推理。

- 作者的亲身经历只能来自作者本人（见 [协作文档与真实经历](协作文档与真实经历.md)），不能为了支持观点补一个故事。
- 案例要说清范围：“这是一家公司的情况”，不能写成普遍规律。
- 一个理由只用一次，不用三个说法重复同一个理由来显得充分。

## 认真对待反方

1. **先把反方讲对**：用反方自己会认可的方式复述他们的观点。这是 Rapoport 规则的第一条，也是“稻草人”的反面。
2. **说出同意的部分**：反方哪里说得对，直接承认。
3. **再说分歧**：分歧在事实、在价值排序，还是在适用场景。很多争论其实是场景不同。
4. **给出边界**：在哪些条件下作者会改变看法。

不点名攻击个人，不揣测反方动机。反驳观点，不反驳人。

## 常见的论证漏洞

写完逐条自查，命中就改：

| 漏洞 | 样子 | 改法 |
| --- | --- | --- |
| 以偏概全 | 我们团队这样，所以大家都该这样 | 写清样本和范围 |
| 非此即彼 | 要么全面上云，要么守着机房 | 补上中间选项 |
| 滑坡 | 今天允许 A，明天就会失控 | 给出每一步的证据，或删掉 |
| 稻草人 | 把反方说成“不想进步” | 按反方的最强版本复述 |
| 诉诸权威 | 某大佬说过 | 引权威的理由，不只引名字 |
| 诉诸人身 | 说这话的人没写过代码 | 回到论点本身 |
| 因果倒置或相关当因果 | 用了 X 的团队都更快，所以 X 让团队变快 | 写成相关，或找因果证据 |

## 写法

- 开头直接亮判断，再给读者一个关心它的理由。
- 正文按理由组织，每节一个理由，小标题写成判断。
- 反方放在读者最可能反对的位置回应，不集中堆到文末。
- 结尾给出边界和读者可以采取的行动，不升华、不喊口号。
- 观点句用作者口吻写（“我认为”“我的建议是”），证据表里记为“建议”，由作者发表前认领。
