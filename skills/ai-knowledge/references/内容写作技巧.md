# 内容写作技巧：让读者读完，并且读懂

一篇好文章同时满足三件事：读者在前几行就知道它和自己有关；每往下读一节都多懂一点；读完能用自己的话讲给别人听。本指南按写作顺序展开，示例均为原创演示。工作台 `写作技巧/` 里有作者自己整理的方法时，两者冲突以作者的为准（事实和安全规则除外）。

## 读者地图

动笔前回答四个问题，写进需求卡（见 [需求卡模板](../templates/brief-template.md)）：

| 问题 | 写法示例 |
| --- | --- |
| 读者是谁 | 会写 Java 接口、没接过统一登录的后端 |
| 他们卡在哪 | 照着文档配好了，但说不清回调里那几个参数各防什么 |
| 读完能做成什么 | 看懂登录回调代码，知道哪一步不能省 |
| 要先补什么 | 只补 Cookie 和重定向，其余前置知识不展开 |

只解释主线用得到的前置知识。读者已经懂的部分一句带过，把篇幅留给新颖或容易误解的地方。

## 立意：核心判断

核心判断是一句能独立成立、带着信息量的话。它决定了标题、开头和每一节取舍。

| 弱 | 强 |
| --- | --- |
| 本文介绍 OIDC 登录流程 | 登录回调里的三个随机值，各自堵住一种冒充 |
| SSO 是一种统一认证方案 | 单点登录省掉的是重复输入密码，每个网站仍然要自己确认你是谁 |
| 总结一次部署失败的排查 | 页面 404 不是代码问题，是构建产物放错了目录 |

自测：把这句话讲给一个同行听，他会不会追问“为什么”？会追问，说明它有信息量，正文就是回答这个“为什么”。核心判断在第 3 步随角度方案一起确定，找法见 [选题与角度](选题与角度.md)。

## 标题

写三个取向不同的标题，选一个，其余放进 review.md。

- **结果型**：直接给出读者能拿走的东西。《看懂 OIDC 回调：state、nonce、PKCE 各防哪一种冒充》
- **问题型**：说出读者心里的疑问。《登录了一次，为什么另一个网站也认得你？》
- **反差型**：纠正一个常见误解，前提是误解真实存在。《单点登录不是共享一个 Cookie》

好标题有具体对象和读者收益，读者看完标题能预期文章会回答什么。中文长文标题一般控制在 30 字以内。标题承诺的内容，正文必须兑现；不用“震惊”“必看”“一文读懂全部”这类无法兑现的词。

## 开头：头几段

读者在开头决定是否继续。尼尔森诺曼集团（NN/g）1997 年的研究发现，79% 的受测者在网页上是扫读而不是逐字读；手机上更是如此。常说的“前 150 字”是编辑经验，没有找到研究出处，意思是：第一屏内就要让读者知道这篇和自己有关。好开头从下面四种里选一种，直接进入，组织方式可参考 [金字塔原理](写作技巧-金字塔原理.md) 的 SCQA：

1. **具体场景**：读者见过的画面。“早上登录了公司邮箱，打开报销系统时它没再要密码。”
2. **反直觉结论**：先给结论，再说为什么。“这三个随机值，少传任何一个，很多身份服务照样让你登录成功，漏洞就藏在这里。”
3. **读者的困惑**：说出他正在卡的地方。“回调地址里那串 code，拿到手为什么还不能直接用？”
4. **结果先行**：先展示做成的东西，再讲怎么做。适合教程和工具类文章。

开头之后两三段内交代文章会解决什么，以及读完能获得什么。背景介绍、名词定义和适用范围说明放到需要它们的地方，不堆在开头。正文中段需要重新抓住注意力时，可以用 [偏航句](偏航句用法.md) 制造一次转折。

## 结构

- 每一节回答读者此刻最可能问的一个问题，小标题写成结论或问题：“code 为什么要换一次才能用”胜过“授权码流程”。
- 用一个贯穿全文的例子。读者跟着同一个用户、同一次登录走到底，比每节换一个例子更容易建立整体图景。
- 难度逐节上升：现象 → 直觉 → 机制 → 实现 → 边界。概念依赖链上，前一节必须为后一节铺好路。
- 讲完一个抽象点，紧接着给一个具体东西：一段代码、一张图、一个数字或一次输入输出。
- 篇幅服从内容。公众号的中文长文常见 2000–4000 字；能更短讲清就更短，不为凑长度加支线。

不同类型的文章，主线不同：

- **讲解**：用最小完整例子检验定义，去掉术语，读者是否仍能说出为什么需要它。
- **复盘**：功能复盘先回答“业务要什么、谁负责哪一步”，再映射到代码；故障复盘先给目标和现象，再展示证据如何一步步改变判断，最后才是根因。
- **测评**：先给结论和适用人群，再给测试方法和记录，最后讲各自的边界，见 [测评](调研-测评.md)。
- **观点**：先亮判断，每节一个理由，在读者最可能反对的地方回应反方，见 [观点](调研-观点.md)。

结构怎么排、小标题怎么写，见 [金字塔原理](写作技巧-金字塔原理.md)。

## 让读者在手机上扫得下去

读者多半在手机上读。下面这些版式手法能帮读者快速抓住重点，按文章需要选用，不必每篇都用：

- **开头一句加粗的判断**：第一段就给出全文核心判断，加粗。读者只读这一句，也知道文章要说什么。
- **编号的判断式小标题**：“1. 回调少一个校验，就能被冒充”。读者知道一共几点、读到第几点。
- **每节一句关键句**：每节最多加粗一句，通常是这一节的结论。加粗多了等于没加粗。
- **一句话引用块**：全文最值得被转述的那句话，可以单独放进引用块（`>`），一篇最多一两处。
- **图片说明**：图后一句话说清图里的关键关系，读者不看图也能跟上。
- **小对比用表格**：2–4 列的对比放表格；更复杂的做成图。

这些手法只改变读者看到重点的速度，不替代内容。没有核心判断时，加粗什么都没用。

## 段落与句子

- 一段一个意思，首句给出这段的结论，后面是理由或例子。
- 手机上一段最好不超过 5 行。长段按意思拆开，不按字数硬切。
- 主语和动作写具体：“浏览器把 code 交给你的后端”胜过“code 被传递到服务端进行处理”。
- 用数字、名字和动作代替形容词：“少输了两次密码”胜过“体验大幅提升”，前提是资料支持。
- 句子之间用逻辑连接（所以、但是、这时候），读者能看出因果；不要用“值得一提的是”“总而言之”这类空过渡。
- 术语第一次出现时用一句日常话解释，之后保持同一个叫法。

## 作者在场

读者愿意追随有判断的作者。正文可以给出明确立场：“如果只能做一件事，我会先把 state 校验补上”，前提是判断有依据，并且这是作者发表时会认领的观点。review.md 的事实核验里把这类句子记为“建议”，让作者确认。

立场和经历要分开。“我会这样做”是观点，可以写；“我上周踩过这个坑”是经历，只能来自作者本人。作者没有提供的经历不写进正文，而是在 review.md 的“可补充的个人经历”里说明位置和建议回答的问题。文章不依赖这些补充也必须完整成立。

称呼读者用“你”，语气平等；不寒暄、不虚构对话，不让读者围观作者和别人聊天。

## 代码

- 只放能说明机制的最小片段，通常不超过 15 行；完整工程放仓库链接或省略。
- 代码前一句话告诉读者看哪里：“注意第 3 行，state 是在跳转前存进会话的。”代码后解释关键行，不逐行翻译。
- 代码块标语言。演示代码在代码前用一句话说明它是演示，并且说明它省略了什么。
- 私有项目的代码重写成原创演示，类名、包名、域名全部换成通用名称（`example.test` 一类保留域名）。

## 类比

最多用一个主类比。先给对应关系，再指出它在哪里失效：“统一登录像公司前台核验身份后发访客证：前台只负责确认你是谁，每个部门仍然自己决定让不让你进。和访客证不同的是，身份服务给每个网站的凭证都单独签发，拿到别的网站不能用。”类比只帮助理解，不能替代机制解释，也不能当证据。

## 不确定性写在原地

证据不足的地方，在说这句话的同一句或下一句写清范围：“以下是 Spring Security 5.8 的默认行为，其他版本请对照文档。”不要在段落末尾补一句“以上仅供参考”，更不要在文末集中堆一段免责声明。

不能确认的结论就把它写窄，或者从正文删掉，记进 review.md 的“存疑”。正文不出现“未核验”“草稿”“本文由 AI 生成”这类生产信息。

## 结尾

结尾给读者带走一样东西：一个判断方法、一张检查清单、一个可以马上做的下一步，或者回到开头的场景给出答案。不喊口号，不写“希望对你有帮助”，不预告“下期再见”。参考链接放在最后一节“参考”，写成“标题：URL”。

## 常见失败与改法

| 读者感受 | 原因 | 改法 |
| --- | --- | --- |
| 开头读不下去 | 先讲背景、定义或免责 | 换成场景、结论或困惑开头 |
| 看完不知道重点 | 没有核心判断，平均用力 | 回到立意，删掉不支撑判断的小节 |
| 中间跟丢了 | 跳步，术语先用后解释 | 读者遍补上缺的那一步 |
| 像说明书 | 只有步骤，没有为什么 | 每个步骤补一句“不做会怎样” |
| 像 AI 写的 | 句式整齐、到处总结、没有立场 | 按 [降AI味指南](降AI味指南.md) 删总结句，加具体例子和作者判断 |
| 不敢信 | 结论没有依据，或者处处免责 | 依据写在原地，结论按证据写窄 |
