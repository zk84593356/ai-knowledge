# 发布合同：工作台、文件与元数据

## 内容工作台

内容工作台是作者放所有内容和个人配置的目录，和代码仓库分开。按顺序找第一个可用的位置：

1. 用户本次明确给出的路径。
2. 环境变量 `AI_KNOWLEDGE_WORKSPACE` 指向的目录。
3. `~/.ai-knowledge/settings.json` 的 `workspace` 字段，例如 `{"workspace": "D:/内容工作台"}`。这个文件只记位置，不放别的配置。

指定的位置读不到时报告原因，不悄悄换成别的位置。三处都没有时，先问作者要不要建工作台，并给出一句可以直接说的话，例如“在 D:\内容工作台 建一个内容工作台”；建法见 [工作台初始化](工作台初始化.md)。作者不建，就按下一节写到项目内目录。

```text
<内容工作台>/
├── 工作台说明.md          # 目录用途和三步上手
├── 用户人设.md            # 作者是谁、写给谁、能说什么，见 用户人设.md
├── 风格参考/
│   ├── 我的写作规则.md     # 作者确认过的规则，写稿时最高优先
│   ├── 我的写作档案.md     # 风格画像，见 风格/加载.md
│   ├── 改稿学习日志.md     # 改稿复盘追加的记录
│   └── *.md               # 作者想学的文章或拆解，例如 如何用 Grok Bot 做内容.md
├── 写作技巧/              # 写作方法，工作台里的版本优先于 Skill 自带的
├── 规范指南/              # 平台规范、话术、运营结论，工作台里的版本优先
├── 品牌资产/
│   ├── 品牌资产说明.md
│   └── <brand-id>/        # 一个品牌一个目录，见 视觉/品牌加载.md
└── 我的项目/
    ├── _briefs/           # 需求卡 <YYYYMMDD>-<topic-slug>.md，选题库.md
    ├── _knowledge_base/   # 资料卡，见 调研/资料卡.md
    ├── _协作文档/          # 给作者的任务单 <YYYYMMDD>-<topic-slug>.md
    ├── 公众号写作/
    │   └── <YYYYMMDD>-<topic-slug>/
    │       ├── article.md # 唯一要发表的长文
    │       ├── review.md  # 发布前核验记录，只给作者看，不发表
    │       └── assets/    # 封面、解释图与 manifest.json
    ├── 推文写作/           # 小红书、微博、X 改编稿，见 写作/平台改编.md
    ├── 短视频逐字稿/        # 口播稿
    └── 历史存档/           # 已发布的项目，按上面三个子目录原样移入
```

目录名里的日期是项目创建日期。

谁能写哪里：

- `我的项目/` 由写作流程写入。
- `用户人设.md`、`写作技巧/`、`规范指南/`、`品牌资产/` 归作者，只读；作者明确要求时才改。
- `风格参考/` 下的规则、档案和日志只按 [风格写回](../风格/写回.md) 和 [改稿复盘](../风格/改稿复盘.md) 的确认流程改。

工作台缺了某个文件（作者删了或旧版本没有），就读 Skill 自带的同名默认文件 `templates/内容工作台/<相对路径>`，并在 review.md 里说明用了默认版本。

## 项目内目录（没有工作台时）

作者不建工作台时，整篇内容写到用户当前项目的 `docs/knowledge/<topic-slug>/`，人设、写作技巧和规范指南都用 Skill 自带的默认版本，不用任何品牌资产：

```text
docs/knowledge/<topic-slug>/
├── brief.md          # 需求卡和角度方案
├── 协作文档.md        # 有作者任务时才有
├── article.md
├── review.md
└── assets/
```

改编稿按需追加在同一目录，例如 `xiaohongshu.md`、`weibo.md`、`口播稿.md`。代码仓库只是素材来源，不改业务代码；交付时再提醒一次可以建工作台。

## 目录和文件名

`topic-slug` 用简短小写英文和连字符，不含路径分隔符、`..` 或 Windows 保留名。目录已存在时，默认在同级新建 `<原目录名>-02` 并依次递增，不覆盖旧文件；用户明确要求“改这篇”“更新这篇”时在原目录修改，保留 `created`、刷新 `updated`，不丢失人工改动。写入前解析真实路径，拒绝越出工作台、项目或授权目录的位置与符号链接。没有写文件能力时，在对话里完整交付两份正文并说明未落盘。

## article.md

Frontmatter 只用下列键，值用双引号字符串和行内数组（同时是合法 YAML 与 JSON 风格）：

| 键 | 约定 |
| --- | --- |
| title | 最终选定的标题 |
| topic | 主题 slug，通常与目录名相同；目录因冲突带了日期后缀时 topic 不变 |
| type | 固定 `"article"` |
| mode | `explainer`（讲解）/ `retrospective`（复盘）/ `evaluation`（测评）/ `opinion`（观点） |
| summary | 一句话摘要，60 字以内，可直接填进平台的摘要栏 |
| tags | 2–5 个检索用主题词，不加井号 |
| created / updated | 实际日期 `YYYY-MM-DD`，updated 不早于 created |
| language | 如 `zh-CN`、`en` |

正文规则：

- **不写一级标题**。标题在平台里单独填写，正文从封面图开始，章节用二级标题。
- 图片只用 `![有意义的 alt](./assets/<文件名>.png)`，路径相对 article.md 所在的主题目录，必须以 `./assets/` 开头，文件必须真实存在。公开平台优先 PNG；SVG 留作可编辑源。
- 不放 Mermaid、HTML 注释、模板变量、脚注语法。Mermaid 在公众号、X、小红书都不会渲染，需要图就导出成图片。
- 表格只用于 2–4 列的小对比。手机上大表格难读，关键对比优先做成图或改成列表。
- 外链集中放在文末"参考"一节，写成"标题：URL"。公众号正文里的外链通常不可点击，读者需要能看到地址。
- 正文里不出现草稿状态、核验日期、工作区状态、审批说明这类生产信息，它们全部写进 review.md。

## review.md

给作者看的发布前记录，不发表。Frontmatter：

| 键 | 约定 |
| --- | --- |
| title | `"<文章标题>｜发布前核验"` |
| topic / mode / language / created / updated | 与 article.md 相同规则 |
| type | 固定 `"review"` |
| status | `"draft"`；只有用户明确说可以发布时才改为 `"ready"`，并在"发布状态"里记下日期和原话 |

正文有一个一级标题，并依次包含这六个二级标题（标题文字固定，便于检查）：

1. `## 发布状态`：当前阶段（停在第几步、在等作者什么）、用户确认记录、作者任务完成情况、平台规则检查结果、发布前还要做的事；发布后记下平台、链接和日期。
2. `## 事实核验`：一张证据表，表头固定为 `| ID | 结论 | 类型 | 依据 | 核验 |`。
   - 类型：项目事实、框架行为、协议原理、通用知识、公开资料、实测记录、推测、建议。
   - 核验：未核验、已核验、推翻、存疑、不适用。写稿者自己写下的结论填"未核验"；只有独立复查（新会话、子 Agent 或用户）才能改成"已核验"。建议类填"不适用"。
   - 项目事实写路径、符号和行号或 Commit；协议原理写规范与章节；框架行为写依赖版本和对应文档；公开资料（官方公告、产品页面、报道、统计）写标题、URL 和访问日期；实测记录写协作文档的路径和条目，内容必须是作者回填的；作者的观点和判断记为建议。
3. `## 公开安全过滤`：哪些真实信息被泛化或删去（公司、行业、域名、内部类名、账号、未修复的安全问题等），以及在文章里的替代写法。只写类别和位置，不复述敏感原值。
4. `## 可补充的个人经历`：文章里留给作者亲身经历的 1–3 个位置，写清在哪一节、建议回答什么问题。没有就写"无"。
5. `## 配图`：每张图的文件、位置、它要让读者看懂什么、制作方式、状态（planned / generated / approved / rejected）；没有配图写明原因。
6. `## 标题与摘要备选`：至少 3 个标题备选及各自的取向，选定的标题和理由。

## 资产台账 assets/manifest.json

有图片就必须有台账，格式见 [视觉规划](../视觉/配图验收.md)。正文引用的每张图都要登记，状态为 generated 或 approved，基础检查通过。

## 平台改编与归档

改编稿的位置、各平台写法和封面尺寸见 [平台改编](../写作/平台改编.md)。作者说已经发布后，在 review.md 的“发布状态”记下平台、链接和日期，再把 `公众号写作/<YYYYMMDD>-<topic-slug>/` 整个移到 `历史存档/公众号写作/` 下，`推文写作/`、`短视频逐字稿/` 里的同名目录也移到 `历史存档/` 下对应的子目录；可用 `scripts/save_article.py`。归档只移动，不改文件内容；目标已存在时停下报告，不覆盖。
