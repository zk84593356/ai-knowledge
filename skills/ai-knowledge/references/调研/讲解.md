# 讲解：把一个概念、技术或方法讲清楚

从“这个概念解决什么问题”确定教学范围，而不是搜集所有百科条目。先写读者遇到的场景，再让一个直觉解释带出准确定义与适用条件。

## 证据与解释

1. 将问题拆成核心定义、运行机制、适用边界和易混淆对比。
2. 能联网且允许时核实关键定义，优先标准、官方文档、研究原文；检索摘要只能帮助定位，不能当作已阅读全文。只引用实际查看的资料。
3. 标明来源适用版本和访问日期。意见、行业经验、假设与被验证事实分开。
4. 将资料改写为读者能理解的教学路径，不连续堆砌引文。

无法访问时仍可解释稳定基础知识，显式说明哪些内容未联网核实。版本、价格、服务行为等变化项不能以确定语气提供“最新”结论。互相冲突的来源要比较时间、版本与适用范围，无法消除冲突则保留分歧。

## 自适应结构

初学者：先讲必要的前置概念，用一个场景走完整流程，再命名术语。普通读者不需要代码也能理解；开发者可增加接口和实现边界。商业或方法论主题用条件、决策和反例，避免伪造精确统计或把经验规则当定律。

复杂关系用图解，简单对比用小表格；每个图节点都在正文有解释。类比明确其失效点。最后用“换一个场景还成立吗”的问题检验理解。

## 防止常见写作失真

“通常”“可以”“必须”不能互换；体验目标、协议和实现产品不能混为同一层次。保留不能由所述机制保证的事项。只解释一条典型流程时，明确它不是所有实现的唯一形式。

## 从概念到文章

概念文章最常见的失败是写成百科词条：定义、特点、优缺点、应用场景。读者读完记住了几个名词，却说不出它为什么存在。

换一种组织方式：先给读者一个他们见过的现象，再问“这是怎么做到的”，用机制回答，最后说清这个机制管不到什么。相邻概念的区别（认证与授权、ID Token 与 Access Token）放在读者最容易混淆的那一刻讲，不集中成一张对比大表。结尾留一个“换一个场景还成立吗”的问题，让读者用刚学到的机制自己推一次。
