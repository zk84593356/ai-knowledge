# 编辑与核验：三遍编辑和一次独立复查

初稿写完后分三遍编辑，每遍只看一类问题。混在一起改，事实问题容易被漂亮的句子盖住。每遍发现的问题当场修正；修不了的写进 review.md。

## 第一遍：事实

逐段读 article.md，对每个影响结论的句子问：它对应证据表的哪一行？

- 对不上任何一行：补证据，或者把句子写窄，或者删掉。
- 证据是“推测”：正文措辞必须是“可能”“一种解释是”，不能写成定论。
- 证据是“建议”：正文要能看出是作者建议，不能写成项目已有能力或历史事实。
- 项目事实、框架行为、协议原理不能混为一层：“本项目做了”“框架默认做了”“规范要求做”分开说。
- 数字、版本、命令、代码和引用原文逐字对照来源。演示代码实际跑过的写明跑过，没跑过的不说能跑。

同时执行公开安全过滤，结果写进 review.md 的“公开安全过滤”：

| 类别 | 例子 | 文章里的处理 |
| --- | --- | --- |
| 组织身份 | 公司名、客户名、行业身份（如某类制造企业） | 泛化成“一个内部系统”或删去 |
| 内部标识 | 域名、内网地址、类名、包名、表名、工单号 | 换成 `example.test`、通用名称或演示代码 |
| 凭据与日志 | 密钥、Token、Cookie、日志原文 | 不出现；需要时写结构，例如 `eyJ...`（已截断） |
| 未修复的问题 | 日志打印敏感值、被注释掉的校验、已知漏洞 | 不写成“我们的系统存在”；可以改写成通用的“常见错误”，且不暴露可定位的细节 |
| 个人信息 | 姓名、账号、邮箱、截图里的头像和水印 | 删除或打码；截图需用户确认 |

review.md 里只记录类别和位置，不复述敏感原值。

## 第二遍：读者

换成目标读者的身份，从标题读到结尾，不看证据表。

- 标题承诺的内容，正文兑现了吗？
- 前 150 字之后，读者知道这篇文章为什么和自己有关吗？
- 每个术语第一次出现时有没有解释？有没有用一个没解释的术语去解释另一个术语？
- 有没有跳步？读者会在哪一句停下来问“为什么”？在那里补一句。
- 代码前有没有说看哪里，代码后有没有解释关键行？
- 每张图在正文里有没有被引用和解释？去掉这张图，读者会不会少懂一点？如果不会，删掉这张图。
- 能不能用一句话复述全文的核心判断？复述不出来，回到立意。

## 第三遍：文字

- 删掉只宣布接下来要讲什么的句子、重复上一段的总结句和空过渡。
- 删掉段落末尾的免责尾巴，把边界移回它所限定的那句话。
- 拆长句，把名词堆叠改回“谁做了什么”。
- 连续三段以上句式相同，或者每节都以总结句收尾时，打破这个节奏。
- 按 [风格加载](style-loading.md) 选中的个人规则逐条回读，搜索命中只提示回读，不机械替换；术语、代码和引用原文不动。
- 最后重读标题、开头和结尾。标题备选和选定理由更新到 review.md，`summary` 控制在 60 字以内。

## 阻断项

下列问题未修复时，交付说明里必须写明文章不可发表：

- 事实错误，或者把推测、建议写成事实。
- 编造的来源、数据、用户经历或运行结果。
- 泄露凭据、私有代码、内部地址、可识别的组织或个人信息，或者暴露未修复的安全问题。
- 正文嵌入了不存在、未登记或未通过基础检查的图片。

信息不足不是阻断项：把结论写窄，在 review.md 标“存疑”，照常交付。

## 独立复查

写稿者无法客观复查自己的证据，所以 review.md 里写稿者整理的结论都是“未核验”。复查需要一个没参与写作的检查者：新会话、子 Agent 或用户本人。

给检查者的输入只有 article.md、review.md 和证据所指向的原始材料（源码、规范、文档），不给写作过程中的推理。检查者逐行处理证据表：

1. 打开“依据”列指向的位置，确认它确实支持“结论”列。
2. 支持就改为“已核验”，并在依据后补一句复查方式，例如“复查：读 `LoginFlow.callback` 第 2–4 行”。
3. 不支持改为“推翻”，部分支持改为“存疑”，并写明原因。
4. 再通读 article.md，找出证据表没有覆盖、但影响结论的句子，追加为新行，核验状态填“未核验”。

有“推翻”的条目时，写稿者修改正文和证据表后再请检查者复查这些条目。宿主不支持子 Agent、用户也没有要求时，不做复查，交付时提醒用户发布前做一次。

## 自动检查

可选的仓库校验脚本只检查结构和有限的敏感模式：文件和字段、标题层级、图片路径与台账、证据表格式。它不能证明事实正确、内容可公开或文章好读。交付时把自动检查结果、三遍编辑的发现和尚未复查的条目分开报告；不要把“没有扫描到密钥”写成“保证不含敏感信息”。
