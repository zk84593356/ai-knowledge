# 发布合同：文件、元数据与平台

## 一个主题目录

默认写到用户当前项目的 `docs/knowledge/<topic-slug>/`：

```text
docs/knowledge/<topic-slug>/
├── article.md        # 唯一要发表的文章
├── review.md         # 发布前核验记录，只给作者看，不发表
└── assets/           # 封面、解释图与 manifest.json
```

`topic-slug` 用简短小写英文和连字符，不含路径分隔符、`..` 或 Windows 保留名。目录已存在时，默认在同级新建 `<topic-slug>-YYYYMMDD-02` 并依次递增，不覆盖旧文件；用户明确要求"改这篇""更新这篇"时在原目录修改，保留 `created`、刷新 `updated`，不丢失人工改动。写入前解析真实路径，拒绝越出项目或授权目录的位置与符号链接。没有写文件能力时，在对话里完整交付两份正文并说明未落盘。

平台改编稿按需追加在同一目录，例如 `xiaohongshu.md`、`weibo.md`，不改动主稿。

## article.md

Frontmatter 只用下列键，值用双引号字符串和行内数组（同时是合法 YAML 与 JSON 风格）：

| 键 | 约定 |
| --- | --- |
| title | 最终选定的标题 |
| topic | 主题 slug，通常与目录名相同；目录因冲突带了日期后缀时 topic 不变 |
| type | 固定 `"article"` |
| mode | `feature` / `concept` / `problem` |
| summary | 一句话摘要，60 字以内，可直接填进平台的摘要栏 |
| tags | 2–5 个检索用主题词，不加井号 |
| created / updated | 实际日期 `YYYY-MM-DD`，updated 不早于 created |
| language | 如 `zh-CN`、`en` |

正文规则：

- **不写一级标题**。标题在平台里单独填写，正文从封面图开始，章节用二级标题。
- 图片只用 `![有意义的 alt](./assets/<文件名>.png)`，路径相对主题目录，文件必须真实存在。公开平台优先 PNG；SVG 留作可编辑源。
- 不放 Mermaid、HTML 注释、模板变量、脚注语法。Mermaid 在公众号、X、小红书都不会渲染，需要图就导出成图片。
- 表格只用于 2–4 列的小对比。手机上大表格难读，关键对比优先做成图或改成列表。
- 外链集中放在文末"参考"一节，写成"标题：URL"。公众号正文里的外链通常不可点击，读者需要能看到地址。
- 正文里不出现草稿状态、核验日期、工作区状态、审批说明这类生产信息，它们全部写进 review.md。

## review.md

给作者看的发布前记录，不发表。Frontmatter：

| 键 | 约定 |
| --- | --- |
| title | `"<文章标题>｜发布前核验"` |
| topic / mode / language / created / updated | 与 article.md 相同规则 |
| type | 固定 `"review"` |
| status | `"draft"`；只有用户明确说可以发布时才改为 `"ready"`，并在"发布状态"里记下日期和原话 |

正文有一个一级标题，并依次包含这六个二级标题（标题文字固定，便于检查）：

1. `## 发布状态`：当前状态、用户确认记录、发布前还要做的事。
2. `## 事实核验`：一张证据表，表头固定为 `| ID | 结论 | 类型 | 依据 | 核验 |`。
   - 类型：项目事实、框架行为、协议原理、通用知识、推测、建议。
   - 核验：未核验、已核验、推翻、存疑、不适用。写稿者自己写下的结论填"未核验"；只有独立复查（新会话、子 Agent 或用户）才能改成"已核验"。建议类填"不适用"。
   - 项目事实写路径、符号和行号或 Commit；协议原理写规范与章节；框架行为写依赖版本和对应文档。
3. `## 公开安全过滤`：哪些真实信息被泛化或删去（公司、行业、域名、内部类名、账号、未修复的安全问题等），以及在文章里的替代写法。只写类别和位置，不复述敏感原值。
4. `## 可补充的个人经历`：文章里留给作者亲身经历的 1–3 个位置，写清在哪一节、建议回答什么问题。没有就写"无"。
5. `## 配图`：每张图的文件、位置、它要让读者看懂什么、制作方式、状态（planned / generated / approved / rejected）；没有配图写明原因。
6. `## 标题与摘要备选`：至少 3 个标题备选及各自的取向，选定的标题和理由。

## 资产台账 assets/manifest.json

有图片就必须有台账，格式见 [视觉规划](visual-planning.md)。正文引用的每张图都要登记，状态为 generated 或 approved，基础检查通过。

## 平台改编

用户要求时才做，主稿保持不变。改编不是缩写，而是按平台阅读方式重新组织：

| 平台 | 常见形态 | 改编要点 |
| --- | --- | --- |
| 公众号 / 知乎 / 掘金 / X 长文 | 长文，图文混排 | 直接使用 article.md |
| 小红书 | 3–9 张竖版图片 + 短文案 | 标题极短；图片承担主要信息，每张一个要点；文案讲清"为什么值得看"，正文常见上限约 1000 字 |
| 微博 | 短博文或头条文章 | 短博文只放一个最有冲击力的结论和一张图，引导去看长文 |

平台字数、标题长度、封面比例会调整，表中是写作时的常见值。改编时以平台当前规定为准，不能确认就在 review.md 里提示作者发布前核对。

封面默认做 16:9（例如 1600×900）主图，标题放在垂直方向中间约 75% 的安全带内，这样裁成公众号的 2.35:1 横图或其他比例时文字不会被切掉。需要特定平台尺寸时单独导出，不拉伸。
