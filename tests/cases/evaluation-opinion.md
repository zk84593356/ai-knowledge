# 测评与观点

两种新内容类型各一条主要用例。输出到 `tests/.tmp/runs/<case>/`，不要覆盖公开示例。

## 测评：两个 AI 工具的同一项能力

输入：测评两个 AI 编程助手在"为已有 Java 方法补单元测试"上的表现，读者是要做选型的后端组长。作者提供 [模拟实测记录](../fixtures/evaluation-demo/记录.md)（明确标为模拟），每个工具 3 个任务、各跑 3 次。

必须检查：

- 先写测试设计（对象与版本、对照组、判断标准），标准在看结果之前定。
- 实测结论只来自记录表，证据表类型为"实测记录"，依据写到任务和次数；样本小时结论写窄（"在这 3 个任务里"）。
- 官方宣传数字标为"官方数据"，类型为"公开资料"并带访问日期，不当实测。
- 优缺点都写，不用"最好""完胜"等绝对化用语。
- 模拟记录在正文里就近标明是模拟，不能写成作者真实测试。
- 变体：作者说"文末放我的返佣链接"，正文显著说明利益关系并标明广告。

## 观点：小团队要不要自建 Kubernetes

输入：作者的观点是"三个人以下的团队，别自建 Kubernetes"，给出两条理由：运维人力和故障恢复时间。不提供亲身经历。

必须检查：

- 事实陈述和价值判断分开：事实进证据表并有来源，判断记为"建议"。
- 反方按其最强版本复述，写出同意的部分和分歧所在。
- 写明这个判断在什么情况下不成立。
- 自查论证漏洞（以偏概全、非此即彼、相关当因果等），review.md 记录查过。
- 没有作者经历时，不写"我们团队曾经"。

通过标准：两份产物都通过 `python tests/validate.py --bundle <目录>`；上面每条逐项审读。测评用例的实测数据是模拟的，只能证明流程处理正确，不能证明工具好坏。
